CHAPTER 08

ソフトウェアと制御

LTEモジュールは「つなげば勝手に通信してくれる部品」ではありません。ホスト（ロボットのメインCPU）がモジュールに指示を出し、状態を見張り、壊れたら立て直す――その仕組みを、ATコマンドを実際に打ちながら学びます。

この章のゴール

  • ホストとモジュールのソフトウェア構成（PPP / QMI / MBIM / ECM / ATソケット）を説明できる
  • Linux搭載SoCとRTOS/MCUで、選ぶ方式がどう変わるかがわかる
  • 基本のATコマンドを打って、SIM・登録・接続状態を読み取れる
  • 起動シーケンス、再接続、ハング時のリカバリを状態機械として設計できる
  • RSRP / RSRQ / SINR / RSSI の意味と目安がわかる
  • FOTA、ログ取得、セキュリティ、遠隔操作時のフェイルセーフの勘所を押さえる

1. 役割分担：ホストとモジュールは「社長と通訳」

LTEモジュールの中には、無線回路（RF: Radio Frequency、高周波部）と、LTEの複雑な手順を処理するベースバンドプロセッサ、そしてそれを動かすファームウェア（FW）が入っています。基地局とのやり取り（第3章のアタッチなど）はすべてモジュールの中で完結します。つまりモジュールは、それ自体が小さなコンピューターです。

一方、ロボットのメインCPU（ホスト）は「何を送りたいか」「いつつなぐか」「おかしくなったらどうするか」を決めます。たとえるなら、ホストは社長、モジュールは海外との電話を代行する通訳です。社長は通訳に「この番号につないで」「今つながってる？」と指示・確認し（＝制御）、つながったら書類を渡して送ってもらいます（＝データ）。この「指示・確認の通り道」と「データの通り道」を分けて考えるのが、この章全体のコツです。

接続方式の比較

方式主な物理IF速度の目安ホスト要件向いている場面
PPPUART / USBシリアルUART速度が上限（〜数Mbps）PPPスタック（pppd, lwIP等）低速・マイコン・どのモジュールでも使いたい
QMIUSBカテゴリ上限まで（Cat-4なら150Mbps級）Linux + qmi_wwan / libqmiQualcomm系モジュール × Linux の定番
MBIMUSBカテゴリ上限までLinux / Windows 標準ドライバベンダー非依存にしたい
ECM / RNDISUSB比較的高速（モジュール内NATを経由）ほぼ設定不要試作初期、手早く動かしたい

※ 速度は目安です。実際はカテゴリ、電波状態、モジュールの実装、ホストの処理能力で決まります。

2. Linux搭載SoCとRTOS/MCUの違い

ロボットのメインボードは、Linuxが動くSoC（System on Chip：Raspberry Pi、NVIDIA Jetson、i.MX などのアプリケーションプロセッサ）であることが多いでしょう。一方、電源管理や足回りを担当する小さなマイコン（RTOS/ベアメタル）にLTEをつなぐ設計もありえます。どちらにモジュールをつなぐかで、ソフトの作り方が大きく変わります。

典型構成：USB接続 → カーネルドライバ（qmi_wwan / cdc_mbim / option（ATポート用シリアル））→ ModemManager ＋ NetworkManager → アプリは普通のソケット。

  • カーネルが対応しているか（USBのVID/PIDがドライバに登録済みか）を最初に確認。古いカーネルでは新しいモジュールが認識されないことがあり、パッチやベンダー提供ドライバが必要な場合も。
  • Yocto / Buildroot など組込みLinuxでは、ModemManager・libqmi・libmbim・usb-modeswitch などのパッケージを含めることを忘れずに。
  • Wi-Fi と LTE を併用するなら、経路の優先度（ルートメトリック）とフェイルオーバーの方針を決めます（例: 構内はWi-Fi優先、途切れたらLTE）。
  • systemd のサービスとして「接続監視デーモン」を置き、ModemManagerの状態を監視して異常時にモジュールをリセットする、という構成がよく使われます。

典型構成：UART接続 → ATパーサ（状態機械）→ ATソケット（MQTT/HTTP内蔵機能）またはPPP＋lwIP。

  • 応答待ちのタイムアウト値はコマンドごとに違います（数百msで返るものもあれば、網への問い合わせを伴い数十秒〜数分かかるものも）。モジュールのATマニュアルに書かれた最大応答時間を表にしておきましょう。
  • URC（非同期通知）がコマンド応答の途中に割り込むことがあるので、受信処理は「1行ずつ読み、応答かURCかを判定する」作りにします。
  • メモリが小さいので、TLSはモジュール内蔵機能に任せるのが一般的。その場合、証明書はモジュールのファイル領域に書き込みます。
  • 低消費電力が重要なら、PSM（Power Saving Mode）や eDRX（extended Discontinuous Reception）といったLTE-M/NB-IoTの省電力機能と、モジュールのスリープ制御ピン（DTRなど）も扱います。

ロボットで映像伝送や遠隔操作をするなら、Linux SoC に USB でつなぐ構成が第一候補です。ソフト資産が多く、スループットも出ます。

ただし「メインCPUが落ちても位置と異常を通報したい」「待機中はメインCPUの電源を切りたい」といった要件があるなら、監視用マイコンにもモジュールの制御線（電源・リセット）をつなぐ、あるいは低速な通報専用の経路を持たせる設計も考えられます。どちらのCPUがモジュールの「持ち主」なのか（電源とリセットの権限）を最初に決めておかないと、後で取り合いになります。

わたしたちのロボットでは

カテゴリが未定でも、ソフト側は次のように「差し替えられる」設計にしておくと安全です。

  • アプリ ⇔ 通信は「ソケット（Linuxのネットワークインターフェース）」で抽象化し、LTEかWi-Fiかをアプリに意識させない。
  • ATコマンドを使う部分は1つのモジュール（ソースファイル）に閉じ込め、ベンダー独自コマンドはそこだけに書く。
  • モジュールの電源（PWRKEY）・リセット・電源スイッチ（ロードスイッチ）をホストのGPIOから操作できるよう回路を用意する（第6章）。

3. ATコマンドの基本：標準と独自

ATコマンドは、1980年代の電話モデムに由来する「文字で命令する」方式です。AT（ATtention＝注目）で始まる文字列を送り、改行（CR）で確定すると、モジュールが結果と OK または ERROR を返します。携帯電話向けのATコマンドは 3GPP TS 27.007（一般・パケット通信）や TS 27.005（SMS）で標準化されています。

書き方意味例
AT+XXX?現在の値を読む（読み出し）AT+CEREG? 登録状態は？
AT+XXX=…値を設定する（設定）AT+CGDCONT=1,"IP","example.apn"
AT+XXX=?設定できる範囲を聞く（テスト）AT+COPS=? 周りの事業者一覧（時間がかかる）
AT+XXX実行するAT+CSQ 電波品質を測って

標準AT（3GPP TS 27.007 等）

先頭が +C のものが中心：+CPIN（SIM）、+CSQ（電波）、+CEREG（LTE登録状態）、+COPS（事業者）、+CGDCONT（APN）、+CGACT（接続の有効化）、+CGPADDR（IPアドレス）、+CFUN（無線ON/OFF）など。どのメーカーでもほぼ同じ意味で使えます。

ベンダー独自AT

メーカーごとに接頭辞が違います（例: Quectelは +Q…、u-bloxは +U…、Telitは #…、SIMComは +C… の独自拡張や +S… など）。詳細なセル情報、バンド固定、FOTA、ソケット、TLS、GNSS、USB構成切替、省電力など、製品開発で本当に必要な機能ほど独自コマンドです。

モジュールを替えたときに困らないために

標準ATでも、応答の細部（空白の有無、省略されるフィールド、エラーコードの出し方）はメーカーやFW版で違うことがあります。パーサは「厳密な文字列一致」ではなく「+CEREG: で始まる行をカンマで分けて数値を取る」ように作り、AT+CMEE=2（エラーを文字で詳しく返す）などで開発中のデバッグをしやすくしておきましょう。

4. やってみよう：ATコマンド・シミュレーター

下の黒い画面は、架空のLTEモジュールにつながったターミナルです。コマンドを入力するか、候補ボタンを押してください。シナリオを切り替えると、SIM未挿入・圏外・APN誤りといった「現場でよくあるトラブル」を再現できます。応答の下に「読み方」の解説が出ます。

トラブル別：最初に打つコマンドの順番
  1. AT に応答がない → 電源・PWRKEY・UARTの配線（TX/RX逆、ボーレート、フロー制御）、USBの認識を疑う。
  2. AT+CPIN? がエラー → SIMの挿入・接触、SIMの電圧、PINロック（SIM PIN と返る）を確認。
  3. AT+CSQ が 99,99 → 電波が見つからない。アンテナ接続、対応バンド（第4章）、バンド設定を確認。
  4. AT+CEREG? が 2 のまま／3 → SIMの契約・ローミング可否・APN・（LTE-M/NB-IoTなら）対応RATの設定を確認。
  5. 登録済みなのに通信できない → AT+CGDCONT? でAPN、AT+CGPADDR でIP、DNS設定、ホスト側のルーティングを確認。

5. 起動シーケンスと接続監視

現場のロボットは、トンネル・エレベーター・倉庫の奥など、電波が途切れる場所を何度も通ります。また、どんなモジュールでもまれに応答しなくなる（ハングする）ことがあります。そこで接続処理は「一度つないで終わり」ではなく、ずっと回り続ける状態機械として作ります。

指数バックオフの擬似コード 
delay = 1s
fail  = 0
loop:
  if try_connect():            # ソケット/PDN/無線の入れ直しを段階的に
      delay = 1s; fail = 0
      wait_until_disconnected()
  else:
      fail += 1
      if fail % 5 == 0: hard_reset_module()   # RESET → PWRKEY → 電源断
      sleep(delay + random(0, delay/2))      # ゆらぎ（ジッタ）を足す
      delay = min(delay * 2, 300s)           # 上限あり

6. 電波品質の指標：RSSI・RSRP・RSRQ・SINR

アンテナの「本数表示」の裏には、いくつかの数値があります。LTEでは基地局が常に送っている参照信号（Reference Signal）を測るのが基本です（定義は 3GPP TS 36.214）。

指標何を測る？たとえ
RSRP
Reference Signal Received Power		つながっている基地局の参照信号1本あたりの受信電力（dBm）。基地局からの距離・遮蔽物を反映。話し相手の声の大きさ
RSRQ
Reference Signal Received Quality		RSRPを帯域全体の電力（RSSI）と比べた品質（dB）。混雑や他セルの影響で悪化。ざわざわした部屋で相手の声がどれだけ目立つか
SINR
Signal to Interference plus Noise Ratio		信号と「干渉＋雑音」の比（dB）。通信速度に最も直結。モジュールによっては独自コマンドでのみ取得可能。声とBGM・雑音の比
RSSI
Received Signal Strength Indicator		帯域内の全電力（自セル＋他セル＋雑音）。大きくても良いとは限らない。AT+CSQ で得られる値はこれ。部屋全体の音量
わたしたちのロボットでは

RSRP・RSRQ・SINR・セルID・バンドを数秒〜数十秒おきに記録し、位置情報と一緒にクラウドへ送ると、「どこで電波が弱いか」の地図が作れます。遠隔操作の映像ビットレートをSINRに応じて自動で下げる制御にも使えます。モーター駆動中だけSINRが落ちるなら、機体内部のノイズ（第6章：アンテナ配置・シールド）を疑いましょう。

7. FOTA：モジュールのFWとホストのOTAを分けて考える

FOTA（Firmware Over-The-Air）は、無線経由でファームウェアを更新する仕組みです。ロボットには2種類の更新対象があります。

LTEモジュールのFW（プロトコルスタック）の更新です。キャリア仕様への追従やセキュリティ・不具合修正のため、量産後も更新が必要になることがあります。

  • 差分更新（デルタ更新）：旧FWと新FWの差分だけを送る方式。全体で数十MBあるFWでも、差分は数百KB〜数MB程度になることがあり、通信量と時間を節約できます。Quectel社は「DFOTA（Delta FOTA）」と呼ぶ独自機能を持ち、ATコマンドで差分ファイルのURLを渡すと、モジュールが自分でダウンロードして更新します。
  • ホスト経由の更新：ホストが差分ファイルをダウンロードし、モジュールのファイル領域に転送してから更新を指示する方式。
  • ベンダーツール：工場や修理ではUSB経由でPCツール（各社のFW書き込みツール）を使って全体を書き換えます。量産基板でもUSBを引き出しておく理由の1つです。
  • 差分ファイルは「旧版→新版」の組ごとに作られるので、現場のモジュールのFW版数を把握していないと配れません。起動時に版数をクラウドへ報告しましょう。

ロボット本体（Linuxイメージやアプリ、マイコンFW）の更新です。

  • A/Bパーティション（2面持ち）で書き込み、起動に失敗したら元に戻す（ロールバック）方式が定番。Linux向けには Mender、RAUC、SWUpdate などのOSSがあります。
  • 更新ファイルには電子署名を付け、ロボット側で検証してから適用します（なりすましFWの防止）。
  • LTEの通信量（従量課金）を考え、差分配信・夜間配信・Wi-Fi接続時のみ配信などのポリシーを決めます。
  • 同時に更新しない：モジュールFOTA中はLTEが使えず、ホストOTAのダウンロードもできません。順番を決め、更新中はウォッチドッグによるモジュールのリセットを止めます（更新中の電源断は文鎮化＝起動不能の原因）。
  • 電源条件：バッテリー残量が十分・充電ドック上・停止中など、安全に更新できる条件を定義。
  • 認証との関係：モジュールFWの更新で無線特性が変わるとは通常考えにくいものの、キャリア認証（IOT）を取った構成のFW版数を変える場合は、キャリアやモジュールベンダーに手続きの要否を確認します（第9章）。
  • 段階配信：まず数台に配って問題がないことを確かめてから全台へ（カナリアリリース）。

8. ログ取得とデバッグ

「現場でつながらない」問題の多くは、ログなしでは原因がわかりません。取れるログは3段階あります。

レベル内容取り方
アプリ／ホスト接続・切断の時刻、再接続回数、RTT、送信失敗自前ログ、journalctl（ModemManagerのログ）
ATレベル送受信したATコマンドと応答、URC、電波指標、セル情報ATパーサで全行を記録（リングバッファに残し、異常時にアップロード）
モデム内部（プロトコル）基地局とのシグナリング（アタッチ拒否の理由コードなど）USBの診断ポート（DMポート）からベンダーツールで取得。Qualcomm系では QXDM / QCAT などが知られ、モジュールベンダーが独自のログツールを提供していることも（利用には契約やNDAが必要な場合あり・要確認）

キャリアとの接続試験やフィールドでの不具合解析では、モジュールベンダーのFAE（技術サポート）にモデム内部ログを渡すよう求められるのが普通です。そのためにも「USBを外に出す」「診断ポートを有効化できる」設計にしておきましょう。なお、出荷品で診断ポートを開けっぱなしにするのはセキュリティ上好ましくないので、量産設定では無効化し、保守時だけ有効にする運用が望ましいです。

9. セキュリティ：ポートを開けず、外向きにつなぐ

LTE回線のIPアドレスは、多くの場合キャリアのNAT（CGNAT: Carrier-Grade NAT）の内側にあるプライベートアドレスで、インターネット側から直接ロボットにアクセスすることはできません。これは不便なようで、実はセキュリティ上は好都合です。ロボットの側から、クラウドへ、暗号化して「外向き」につなぐのが定石です。

  • 機体ごとの証明書・秘密鍵（全台共通の秘密を持たない）
  • サーバー証明書の検証を無効にしない（開発用の設定を量産に持ち込まない）
  • ファームウェア・更新ファイルの署名検証とセキュアブート
  • デバッグ用ポート（UARTコンソール、モジュールの診断ポート、SSH）の量産時無効化
  • 時刻同期と、証明書の期限切れ前に更新する仕組み
  • SIMの不正利用対策（SIMロック、IMEIとSIMの紐付けなどSIMサービス側の機能）

10. ロボットの遠隔操作：遅延・ジッタ・パケロスとフェイルセーフ

LTEはWi-Fiより広い範囲で使える一方、遅延が大きく、しかも揺らぎます。目安として、LTEの往復遅延（RTT）は良い条件で数十ms、混雑時やセル切替（ハンドオーバー）時には数百ms〜1秒以上に跳ねることもあります。上り（ロボット→クラウド）の帯域は下りより狭いので、映像を送る遠隔操作では上りがボトルネックになりがちです。

問題何が起きる主な対策
遅延（レイテンシ）操作してから動くまで・映像が届くまでが遅いサーバーを近い地域に置く、映像の解像度・フレームレートを下げる、低遅延コーデック設定、ロボット側での自律（障害物停止は機体で判断）
ジッタ（遅延の揺らぎ）指令が固まって届き、動きがカクつく指令にタイムスタンプと連番を付け、古い指令は捨てる。速度指令は「一定時間だけ有効」とする
パケットロス映像の乱れ、指令の欠落映像はUDP系（WebRTC等）でFEC・再送を調整、指令は最新値のみ意味を持つ設計に。TCPの再送待ちで遅れた指令を実行しない
通信断数秒〜数分つながらない下のフェイルセーフへ。復帰後は自動で操作を再開せず、オペレーターの確認を求める
帯域不足（特に上り）映像が送りきれず遅延が積み上がるSINR・送信キューの長さを見てビットレートを自動調整（適応ビットレート）。カテゴリ選定（第5章）で上り速度を確認
フェイルセーフは「通信が必ず切れる」前提で
  • デッドマン（ハートビート）方式：オペレーターからの指令（またはハートビート）が一定時間（例: 数百ms〜1秒、ロボットの速度と停止距離から決める）届かなければ、自動で減速・停止する。
  • 段階的な縮退：遅延が増えたら最高速度を下げる → 途絶えたら停止 → 長時間途絶えたら安全な姿勢・場所で待機し、通報する。
  • 通信に頼らない安全機能：非常停止ボタン、衝突検知、障害物センサーによる停止は、ネットワーク経由ではなく機体内で完結させる。
  • 停止時間・停止距離・縮退の閾値は、機械安全のリスクアセスメント（第9章コラム）で根拠を持って決め、記録に残す。

まとめ

  • モジュールは「通訳」。ホストは制御（ATコマンド）とデータの通り道（PPP/QMI/MBIM/ECM/ATソケット）を分けて扱う。
  • Linux SoCならUSB＋QMI/MBIM＋ModemManagerが定番。RTOS/MCUならUART＋ATパーサ＋PPPまたはATソケット。
  • 標準AT（3GPP TS 27.007）は共通、独自ATはメーカー依存。独自部分をソフト上で隔離しておく。
  • 接続処理は状態機械。タイムアウト、指数バックオフ＋ゆらぎ、RESET/PWRKEY/電源断による段階的リカバリを設計する。
  • RSRP（強さ）・RSRQ／SINR（質）を記録し、映像ビットレート制御や設置場所の改善に使う。
  • モジュールFOTAとホストOTAは分けて計画。版数管理と「同時に更新しない」ルール。
  • 待ち受けポートを開けず、機体ごとの証明書でTLSの外向き接続。通信断時は自動で安全側へ。

用語

ホスト
モジュールを制御するメインCPU（SoCやマイコン）。
ATコマンド
「AT」で始まる文字列でモデムを制御する方式。携帯向けは3GPP TS 27.007等で標準化。
URC
Unsolicited Result Code。コマンドを送っていないのにモジュールから届く通知（例: 登録状態の変化）。
PPP
Point-to-Point Protocol。シリアル回線上でIPを運ぶ方式。
CMUX
1本のシリアル回線を複数の論理チャネルに分ける多重化方式（3GPP TS 27.010）。
QMI
Qualcomm MSM Interface。Qualcomm系モデムの制御プロトコル。Linuxでは qmi_wwan / libqmi。
MBIM
Mobile Broadband Interface Model。USB-IFが定めたモバイルブロードバンド機器の標準USBインターフェース。
ECM / RNDIS
USB経由でEthernetアダプタとして見せる方式（ECMは標準、RNDISはMicrosoft由来）。
ModemManager
Linuxでモデムを検出・制御する標準デーモン。NetworkManagerと連携する。
APN
Access Point Name。どの接続先（ゲートウェイ）につなぐかを示す名前。SIMの契約で決まる。
PWRKEY
モジュールの電源ON/OFFを指示する端子。一定時間のパルスで操作する。
RSRP / RSRQ / SINR / RSSI
LTEの電波の強さ・品質の指標（本文6節）。
FOTA / DFOTA
無線経由のFW更新／その差分更新版（DFOTAはQuectelの呼称）。
CGNAT
キャリアが多数の端末を少数のグローバルIPにまとめるNAT。外から端末に直接届かない。
MQTT
IoT向けの軽量なpublish/subscribe型プロトコル。
指数バックオフ
失敗するたびに待ち時間を倍にしていく再試行方法。
